# routeplanner

Shortest and fastest routes over a road network, written from scratch in Python
with no dependencies. Dijkstra, A* and bidirectional search over one
implementation, two cost models that genuinely disagree, and search statistics
on every result so the claims about one algorithm beating another can be
checked rather than repeated.

```
$ routeplanner route n0202 n3737 --fastest
astar, fastest
  50.19 km, 34.4 minutes, 22 segments
  1,141 expanded, 1,443 pushed, 4,202 relaxed, peak frontier 208

      1.33 km  C Lane
      1.99 km  1st Avenue
     44.21 km  Ring Motorway
      1.33 km  36th Avenue
      1.33 km  AL Lane

  44.21 km of that is motorway
```

- **69 tests**, Python 3.10–3.12, standard library only
- A 1,600-intersection network with three road classes, regenerated by CI and
  compared byte for byte
- The heuristic's admissibility is **tested against the real network**, not
  asserted in a comment

## Quick start

```bash
git clone https://github.com/umer-78/route-planner.git
cd route-planner
pip install -e ".[dev]"
pytest -q                          # 69 tests

routeplanner stats
routeplanner route   n0202 n3737              # shortest
routeplanner route   n0202 n3737 --fastest    # fastest
routeplanner compare n0202 n3737              # every algorithm, side by side
routeplanner weights                          # what inflating the heuristic costs
routeplanner bench
routeplanner nearest 31.45 74.25
```

## The fastest route is 3.6 km longer and half an hour quicker

A router with one cost model cannot answer the question people actually ask.
The same pair of intersections, minimising distance and then time:

| | distance | time | roads | motorway |
| --- | --- | --- | --- | --- |
| shortest | **46.55 km** | 64.2 min | 8 | 0 km |
| fastest | 50.19 km | **34.4 min** | 5 | 44.21 km |

Over 300 random pairs the two routes differ on **95%** of them; where they
differ the fastest is 1.49 km longer and 8.2 minutes quicker on average. That is
why `length` and `speed` are stored separately on every edge rather than
collapsed into one number at load time — a graph that stores only travel time
cannot answer for distance, and vice versa.

## A* is only exact if the heuristic never overestimates

The heuristic is the great-circle distance to the goal, which no road can beat,
so it never overestimates and A* returns the same route Dijkstra does — it just
looks at less of the map to find it.

```
$ routeplanner bench -p 60
60 random pairs over 1,600 nodes

algorithm         mean expanded   median saving   seconds
dijkstra                    831           1.00x      0.14
a*                          275           3.95x      0.09
bidirectional               603           1.55x      0.10
```

Two things about that heuristic are easy to get wrong, and both are tested:

- **Euclidean distance on raw latitude and longitude is not admissible.** A
  degree of longitude is 111 km at the equator and 95 km at this network's
  latitude. Treating the two axes alike overestimates east-west distance, and an
  overestimate is exactly what breaks the guarantee.
- **The travel-time heuristic must divide by the fastest speed anywhere in the
  graph**, not by the speed of the road the search is standing on. Assuming the
  rest of the journey happens at 35 km/h overestimates the time whenever a
  motorway lies ahead.

`test_the_straight_line_never_exceeds_the_road_distance` checks admissibility
over 150 random pairs of the real network by computing the true driving distance
and comparing. A heuristic asserted to be admissible in a docstring is a
heuristic nobody has checked.

Bidirectional search saves less here than the textbook suggests — 1.55× rather
than the square-root improvement — because the grid is bounded. Dijkstra's
expanding disk hits the edge of the map and stops growing long before the two
smaller disks would have won, so the saving is real but modest, and A* beats it
comfortably. Reporting 1.55× rather than the theoretical figure is the point.

## Inflating the heuristic a little is worse than not inflating it at all

Multiply the heuristic by a weight above 1 and it stops being admissible: the
search gets greedier, finishes sooner, and no longer guarantees the shortest
route. The expected trade is a smooth one. It is not:

```
$ routeplanner weights -p 40
 weight  expanded  reexpanded       km   excess  speedup
    1.0       239         0.0   17.289    0.00%    1.00x
    1.1       382       196.3   17.299    0.06%    0.63x
    1.2       378       236.2   17.299    0.06%    0.63x
    1.3       394       292.0   17.300    0.06%    0.61x
    1.5        31         1.9   17.302    0.07%    7.63x
    2.0        27         0.3   17.391    0.59%    8.87x
    3.0        26         0.0   17.391    0.59%    9.10x
```

Between 1.1 and 1.3 the search expands **more** nodes than the exact one — a
0.61× "speedup" — while giving up the optimality guarantee for a 0.06%
improvement in nothing. The `reexpanded` column is why: a mild inflation makes
the heuristic inconsistent without making the search meaningfully greedier, so
it pays for two to three hundred re-expansions per query and buys nothing with
them. At 1.5 the greed finally dominates and the search collapses to 31 nodes.

So the useful settings are 1.0 and 1.5-and-up; the range in between is the worst
of both worlds. At 1.0 the re-expansion count is **exactly zero**, which is what
a consistent heuristic promises and
`test_a_consistent_heuristic_causes_no_reexpansions` holds it to.

## Closing a node permanently can return the wrong route

Most A* implementations put a settled node in a closed set and never look at it
again. That is correct when the heuristic is *consistent* — and admissible is
not the same as consistent. Here is a four-node graph where the difference
shows:

```
        8
   S ───────────────► A ──────► G
   │                  ▲    5
 5 │              2   │
   └──────► C ────────┘

   h(S)=2   h(A)=1   h(C)=7   h(G)=0
```

The heuristic never overestimates: the true costs to the goal are S=12, A=5,
C=7, so every estimate is under. But consistency also requires
`h(n) ≤ cost(n,m) + h(m)` for every edge, and `C → A` costs 2 while `h(C) − h(A)`
is 6. One edge is enough:

| | route | cost |
| --- | --- | --- |
| reopening closed nodes | `S → C → A → G` | **12** |
| closing them permanently | `S → A → G` | **13**, 8% worse |

A* expands `A` early with `g = 8` via the direct edge, then reaches `C` and
discovers a 7-cost route to `A` — which the closed set throws away. The graph
was found by searching small random graphs for a case where the two disagree,
then reduced by hand; `tests/conftest.py` has it, and three tests check that the
heuristic really is admissible, really is inconsistent, and really does need the
re-expansion.

`--no-reopen` reproduces the failure from the command line.

## The shortest route is not unique

A grid has many paths of exactly the same length, so "the shortest route" is a
set and which member comes back depends on how an algorithm settles ties.
Between the same two intersections, Dijkstra and bidirectional search both
return 25.28 km routes — that take different amounts of time.

That is not a bug in either, and `test_the_shortest_route_is_not_unique` pins it
so it does not get "fixed" into one. It is also why the tests compare *costs*
rather than node lists: an equality check on the route would fail for a correct
implementation.

## The network

```
$ routeplanner stats
1,600 intersections
5,914 directed edges
average out-degree 3.7
fastest road 100 km/h

edges by speed:
     100 km/h      58
      60 km/h   1,248
      35 km/h   4,608
```

A 40×40 grid with local streets at 35 km/h, arterials every fifth row and column
at 60, and a ring motorway at 100. Eight per cent of ordinary blocks are dropped
so the grid is not a perfect lattice where every route is the same length.

That thinning can strip an intersection of all four of its roads, and it did —
`n2612` came out with none. An intersection with no roads is not an
intersection, and a router cannot be exercised on a network where some pairs
have no answer for reasons that are an accident of the seed. So the generator
finds anything cut off and gives it one road back, and **prints how many**:

```
$ python tools/make_network.py
1,600 intersections, 5,914 directed edges, average out-degree 3.7
1 road(s) added to reconnect intersections the thinning cut off
every intersection reaches every other: True
```

A generator that quietly repairs its own output is a generator whose output
nobody can reason about. CI regenerates the network and fails if a byte differs,
so every number in this README reproduces from a clean checkout.

## Layout

```
src/routeplanner/
  graph.py      nodes, directed edges, haversine, routes
  search.py     one search function; Dijkstra is A* with a zero heuristic
  cli.py        route, compare, weights, bench, stats, nearest
tools/          the network generator, seeded and reproducible
data/city/      1,600 intersections as two CSV files
tests/          69 tests
```

Dijkstra and A* are one implementation, not two. Written separately they drift,
and then the tests that compare them are comparing two things that differ in
ways nobody tracked.

## Tests

```
$ pytest -q
69 passed
```

The ones that matter are the ones that would pass against a wrong
implementation of the algorithm as usually written: that all three searches
agree on cost over 60 random pairs, that a consistent heuristic causes exactly
zero re-expansions, that an admissible-but-inconsistent one needs them, that
mild inflation is *slower*, and that bidirectional search does not stop at the
first node both frontiers have touched — the first meeting point is not
necessarily on the shortest path.
